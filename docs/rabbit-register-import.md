# Rabbit Register XML import

Account Settings → Import & export → Import from Rabbit Register accepts Evans Rabbit Register XML exports. Follow [Evans’ export instructions for RingMaster (PDF)](https://evsoft.us/files/Exporting_to_RingMaster.pdf), using **File → Data Management → Export Data as XML File → RingMaster**. The previously supported **Other** XML export remains accepted. The import screen links directly to this guide in a new tab, above file selection. Choose a personally owned, non-demo destination herd and name the source database. Reuse that source name for later exports of the same database; use a different name for another breeder's database. Source names are trimmed and case-insensitive. Filenames are not identities.

The file is parsed locally. Preview and saving require a network connection. Nothing is saved during preview. The final invoker RPC revalidates the payload and saves animals, source identities, source snapshots, dated weights and history in one transaction. Concurrent imports into a herd are serialized. Existing source IDs are reused on retry. Original XML files are never modified. No real user import or production deployment is performed by the implementation tests.

## Supported data

- Animals: source CID, name, tattoo, breed, variety, sex, birth date, registration and grand champion numbers, legs, comments, sire/dam links and status. Active storage remains active. Archive storage becomes deceased when it has a death date, sold when it has a sale date, otherwise archived. Archived animals are never made active just to import them.
- Storage codes `Active_I`–`Active_IV` and `Arch._I`–`Arch._IX` determine membership independently of the label after the colon, including repeated labels such as `Arch._II:Arch._II`. Legacy `:Active` / `:Archive` labels remain supported for other codes; unrecognized storage areas still block import. The original storage field and XML bytes are retained unchanged.
- Field reads accept capitalization/punctuation variants and the documented aliases `Ear_Number` / `Ear_Num`, `Grand_Ch_Num` / `Grand_Ch.__Num`, `WID` / `ID` for show identities, `Winnings` / `WINS`, and `ForSalePprice` / `ForSalePrice`. This covers mixed-case parent, picture, feed/weight, litter and wool fields through native history linking. Source fields and XML bytes are not renamed. Conflicting nonblank aliases block import instead of selecting an arbitrary value. Reimports compare equivalent identity fields and preserve the first snapshot and current management values.
- Missing names fall back to the ear number, then the visible label `Rabbit Register #CID`. Original blank fields remain blank in the source snapshot.
- Source IDs remain distinct. An exact existing-animal candidate requires name, tattoo, rabbit species, breed, variety, sex and birth date to match. Users explicitly choose a candidate or a separate new animal; tattoo alone never merges records. Existing animals retain their core fields and parent links. New source measurements and missing management details can be linked without replacing current values.
- Dated weight measurements convert from grams to pounds (453.592 grams per pound). The supported XML format stores grams; conversion to pounds is automatic and there is no unit selector. Positive, dated measurements are linked to normal weight history, including previously imported animals. Stable source links and matching legacy measurements prevent duplicate weights. Blank dates and zero weights remain in source history without creating chart points. Profile weight snapshots have no date and are retained as snapshots, without inventing a measurement date.
- Contacts become herd contacts with person/rabbitry information and stable source IDs. Account → Contacts & rabbitries lets the owner review the current and proposed values, fill empty fields, replace contact details, or create a show profile. Login identity/email never changes through this import.
- Buyer and seller IDs link to contacts in animal management. Purchase date/cost, death/sale dates, cage and custom fields are available under Animal details → Housing, contacts & custom details. Existing values take precedence over import fills. All unknown animal fields outside the standard field list are retained as labelled custom values.
- Sale records with sale date, amount or buyer information appear in the normal sales dashboard with source provenance. Unknown payment history stays unknown; no payment, receipt, balance due or active listing is fabricated from an imported sale amount.
- Source litters enter normal breeding/litter tracking. Unknown breeding dates and sires stay blank. Litters without an identifiable doe stay in source history with a warning. Removal-complete flags determine completed status. Source total born and deaths remain distinct from born-alive/stillborn counts. Imported litters offer Manage offspring: link already-entered rabbits first, or explicitly create the unrecorded remainder after entering the sire, birth date and weaning details. Missing imported counts stay unknown during ordinary tracking edits; they are never filled with invented zeros.
- Litter cards expose dated total-litter weights and cumulative feed weights. Wool harvest history is available alongside animal weight history, with fleece/grade weights in grams and fiber measurements kept separately from animal body weight. Both histories support adding and correcting manual or imported records online with revision checks. Incomplete litter measurements remain in source history.
- Show results enter normal show history, link to animals when available, display judges, placements, leg/youth flags and counts, and feed pedigree major-win details. A source rank of Hide suppresses that result on pedigrees. Total source legs are not increased again for imported individual leg flags.
- Original contacts, litter/show/measurement records, source snapshots and supplemental sections remain owner-private in Rabbit Register history. Nested contact categories remain XML text. Mileage, picture references, growth, finances, journal and sweepstakes sections are retained without pretending to create photos or accounting activity.
- Rabbit Register history is accessible from Account Settings, animal details and Breedings & litters. It paginates source records and shows original fields and import review decisions.

## Review and validation

The observed Other exporter crashes after a closed `CritterWeights` section without closing `ExportedData`. This exact structural case can be recovered in memory by adding the final root closing tag. A warning requires acknowledgment because other sections may have been omitted by the source crash. XML cut off inside a record or section is rejected. Recovery does not claim the export is complete.

Unknown sex needs an explicit Buck/Doe selection. Missing source parents remain unlinked only after acknowledgment, with the original IDs retained. No placeholder ancestors are invented. Parent-role conflicts and pedigree cycles block saving; the screen offers explicit omissions of the problematic links while retaining their original values. Users may instead correct the source and export again. Server validation independently checks source IDs, dates, weights, parent sexes and cycles even if the client controls are bypassed.

Only UTF-8 XML with the `ExportedData` root and documented Header/Animals/Contacts/Winnings/Litters/CritterWeights/LitterWeights/Wool/Mileage/PictureMap/GrowthData/Finances/Journal/SweepsPoints sections is accepted. Unknown sections are rejected rather than silently dropped. DTD/entity declarations, repeated fields/sections/source IDs, malformed XML, invalid/future normalized dates and invalid measurements are rejected. Date placeholders `0100-01-01`, `0100-01-02`, `0100-01-03` and `2100-12-12` stay missing in normalized values and remain unchanged in original history. Dave documented January 1, year 100 and December 12, 2100; the user also approved treating January 2 and 3, year 100 from his sample as blank. Limits: 10 MB file, 2,000 rabbits, 20,000 history records. The server also bounds payload size.

First imported snapshots are immutable through the importer. Reimports preserve existing core details and first snapshots. Supplemental animal fields can fill empty management values without replacing current data. Native litter/show/sale/measurement identities are reused rather than synchronized over later edits. Changes to a previously imported CID's name, tattoo or breed block the import so the user can check the source identity. Other changes to animal snapshots generate preservation warnings. A new source label is not a substitute for reconciling changes to the same database.

## Initial sample validation

The supplied Other XML contains 592 rabbits (35 active), 17 contacts, 628 show records, 97 litters and 50 dated weights. It has three unknown sexes, eight rabbits with neither name nor tattoo, four missing animal-parent references, and two litters referencing another absent sire. The parser identifies four cycle-closing links for explicit review. These problems were not apparent from the earlier count-only inspection.

The sample was parsed locally and committed/retried only in an isolated PostgreSQL fixture using test-only sex selections and link omissions. Those choices are not user decisions and must not be copied into a real import. The test verifies 592 animal inserts and 792 history inserts with no additions on retry. Personal sample data is not committed to the repository. Another breeder's export is still needed to broaden compatibility validation.
